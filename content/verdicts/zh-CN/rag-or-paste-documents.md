## 议会裁决
理事会一致建议小团队**切勿在初期从零自建 RAG**。首选方案是直接利用长上下文大模型投喂文档进行 MVP 验证，或直接采用现成托管/开源工具（如 Dify）。只有当数据规模、高频调用成本、严格权限隔离或本地合规成为实质瓶颈时，再考虑引入检索链路，且仍应优先选用成熟方案而非自研。综合置信度：8/10。

## 共识点
* **坚决避免过早自建：** 自建 RAG 的切分、嵌入、召回调优及持续评测人力成本极高，小团队极易陷入工程泥潭。
* **低成本快速上线：** 小团队语料多在百万 token 内，直接投喂模型不仅数小时内即可上线，且全局推理效果往往优于粗糙切片的向量检索。
* **清晰的演进路径：** 一致认同“长上下文验证价值 -> 托管/开源 RAG 承接业务 -> 极端需求下才考虑深度自建”的渐进策略。

## 分歧点
* **迁移到 RAG 的触发条件：** DeepSeek 强调成本取决于“文档量 × 调用频次”，高频场景下 Token 成本骤增会倒逼团队快速放弃纯上下文方案；GPT-6 Luna 则更关注长文本引入的上下文噪声和延迟瓶颈；Gemini 认为纯 Prompt 仅用于极短期验证，随后应立即转入成熟框架。

## 风险与保留
* **成本与延迟突增：** 若文档量大且并发查询频繁，反复全量输入将导致 API 费用暴涨和响应延迟不可接受。
* **权限与合规风险：** 直接向公有云模型输入企业数据存在泄露隐患，且纯 Prompt 方案无法原生实现组织内细粒度的文档权限隔离。
